# План роботи

Не для репозиторію. Для себе.

---

## Правила, які рятують проєкт

1. **Деплой у першу годину, порожнім.** До будь-якої логіки. Половина take-home вмирає на тому, що деплой лишили на кінець.
2. **Кожен блок закінчується задеплоєним станом.** Ніколи не накопичуй два блоки незадепложеного коду.
3. **`README.md` → секцію "Known limitations" дописуй по ходу.** Через сім годин ти не згадаєш, чому щось не зробив.
4. **Коли час горить — ріж у порядку:** search → drag-n-drop для move (лишити move через меню) → keyboard shortcuts → versioning UI (логіку в моделі лишити).
5. **Ніколи не ріж:** деплой, демо-акаунт із seed, стани помилок, README.

## Блок 0 — рішення зафіксовані (не переграємо)

| Питання | Рішення |
|---|---|
| Дерево | `parent_id` + `path text`, materialised path |
| Конфлікт upload/move | Діалог Keep both / Replace / Skip, default Keep both |
| Конфлікт rename | Блок + inline-помилка з пропозицією імені |
| Видалення | Soft (`deleted_at`), без UI кошика |
| Авторизація | Тільки в Nest, RLS = deny-all backstop |
| Перегляд файлу | Модалка + shallow routing, не окремий маршрут |
| Список файлів | Таблиця, не сітка карток |
| Унікальність імені | `(parent_id, lower(name))` без фільтра по `status` — конфлікт спрацьовує на `init` |
| Порядок сортування | Generated-колонка `sort_rank` (folder 0, file 1), усе ASC |
| Видалене + шара | Спершу permission, потім `deleted_at`: `none` → 404, дозволено+видалено → 410 |
| Стани екранів | Будуються в тому ж блоці, що й екран, не в кінці |

Переграти будь-що з цього після блоку 2 — дорого. Тому не переграємо.

## Блок 3 — upload (~2.5 год)

**Мета: найпомітніша частина UX працює бездоганно.**

- [ ] `POST /files/init` → node `status='uploading'` + signed upload URL
- [ ] `POST /files/:id/complete` → перевірка об'єкта, `size_bytes`, `status='ready'`
- [ ] Ловити `23505`, не робити `SELECT` перед `INSERT`
- [ ] `23505` проти `uploading` рядка старшого за 15 хв → soft-delete його і **один** ретрай інсерту
- [ ] NFC-нормалізація імені на вході
- [ ] Magic bytes: перевірка в браузері для фідбеку + **авторитетний `Range: bytes=0-7`** у `complete`
- [ ] Фронт: drag-n-drop зона, черга, **per-file progress / cancel / retry**
- [ ] Діалог конфлікту з «apply to all»
- [ ] Sweeper для `uploading` старших за 15 хв
- [ ] Деплой

**Definition of done:** кинув 5 PDF одразу, один із дублем імені, один скасував посеред — усе поводиться передбачувано.

**Найлегше зіпсувати:** один файл падає — падає вся черга. Не роби так.

## Блок 4 — перегляд і операції (~2 год)

- [ ] `GET /files/:id/download-url` → TTL 60с
- [ ] PDF viewer у модалці + shallow routing
- [ ] Signed URL протух при відкритому PDF → прозорий refetch
- [ ] `PATCH /nodes/:id` — rename + move одним ендпоїнтом
- [ ] Детектор циклу: `target.path.startsWith(source.path)` → 400
- [ ] Move гілки: один `UPDATE` префіксів у транзакції
- [ ] `DELETE /nodes/:id` — каскадний soft delete по префіксу, **`shares` не чіпає**
- [ ] `GET /nodes/:id/stats` — **реальні цифри для діалогу видалення**
- [ ] **Кімнати теж:** `PATCH /rooms/:id`, `DELETE /rooms/:id` + унікальний індекс
      `(owner_id, lower(name))`, ловимо `23505` → `NAME_CONFLICT`. Знайдено в блоці 2:
      root-нода має `parent_id IS NULL`, тож `nodes_name_uniq` на кімнати не діє, і
      дві кімнати з однаковою назвою проходять. Корінь проблеми не в назві, а в тому,
      що кімнату не можна ні перейменувати, ні видалити — помилка при створенні
      незворотна. Обидва додавання розширюють заморожений контракт **свідомо**
- [ ] **Рядкове меню:** Open / Rename / Move / Delete — кнопка `⋯` у рядку плюс права
      кнопка як прискорювач. Тільки правої кнопки замало: її не видно, на тачі немає,
      клавіатурою не дістати. Copy/Duplicate **не робимо** — немає ні в ТЗ, ні в
      контракті, а копія папки тягне рекурсивний insert і копіювання блобів
- [ ] **Стани PDF-модалки — тут:** скелет сторінки / «Preview unavailable» + Download / протух URL → refetch
- [ ] Оптимістичний rename/move з роллбеком і тостом при фейлі
- [ ] Деплой

**Definition of done:** діалог видалення папки показує «3 folders, 47 files, 128 MB» — з бекенду, не з того, що фронт встиг завантажити.

## Блок 5 — шаринг (~2.5 год)

**Найризикованіший блок. Тут баг = витік даних.**

- [ ] `POST /nodes/:id/shares` — обидва режими
- [ ] Токен 256 біт, у БД **тільки SHA-256 hash**
- [ ] `GET /s/:token` — `@Public()`, `Referrer-Policy: no-referrer`, rate limit
- [ ] `resolvePermission` — **максимум по ланцюжку предків**, не перший знайдений
- [ ] Три відповіді для named share: анонім / збіг email / не збіг
- [ ] Повідомлення про не-збіг будується з email **запитувача**, не grantee
- [ ] Pending share по `grantee_email`, резолв при signup
- [ ] `DELETE /shares/:id` — revoke
- [ ] `<DataRoomView permission="viewer" />` — read-only як проп на все дерево, **не двадцять `{isOwner && ...}`**
- [ ] **Порядок перевірок:** permission проти вузла разом із тумбстоунами, потім `deleted_at`. `none` → 404, дозволено+видалено → 410
- [ ] `410` при видаленні під час перегляду → екран із поясненням і маршрутом назад
- [ ] **Стани панелі шарингу — тут:** skeleton / «Not shared yet» / retry
- [ ] **Юніт-тести `resolvePermission` тут же, не потім** — включно з кейсом «валідна шара на видалений вузол → 410, вгаданий токен → 404»
- [ ] Деплой

**Definition of done:** інкогніто-вікно відкриває публічне посилання без логіну. Чужий залогінений юзер на named share бачить осмислене повідомлення, не 403. Власник видаляє папку під відкритою вкладкою реципієнта — той бачить 410-екран, а не спінер.
